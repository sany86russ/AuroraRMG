## R-01: native схемы

Установленный `HeroesOldenEra_Data/StreamingAssets/map_schemas/Default.mrmg.json` содержит 14 zone classes, 7 main object classes, 6 layouts, 63 mandatory groups и 3 content count limits. В этом файле условия используют `difficulties`, `richnesses`, `flagOn`, `flagOff`, `zoneAreaMin`. Флаги текущих таблиц — `SingleHero` и `Symmetrical`.

Нативные модели дополнительно имеют условия min/max размера, площади, расстояния от первичного старта и прогрессии. Из метаданных и выбранных инструкций установлено:

- `RmgSchema.Conditions` RVA конструктора `0x29DE560`: восемь min/max значений по умолчанию равны −1.
- `RmgSchema.ConditionalParam<int>` RVA конструктора `0x179C2B0`: начальный вес `1.0`, fallback по умолчанию false.
- `bpp.npl<int>` RVA `0xBC50A0`: выбирает обычные строки, одновременно удовлетворяющие AND и OR; при отсутствии кандидатов берёт fallback строки без повторной проверки их условий. При отсутствии любых строк возвращает переданное значение по умолчанию.
- `bpp.npm` RVA `0x2AF80C0`: пустая группа условий подходит, отрицательные min/max не ограничивают выбор; недоступный отрицательный контекст величины тоже не участвует в сравнении; числовые границы включительные.

В `NativeSchemaEvaluator` реализован собственный алгоритм по этим правилам формата. Последовательность расходования random values и геометрия native генератора не копируются и не обещаются. Неизвестное условие сохраняется при чтении/экспорте, но его оценка прекращается с явной ошибкой. Нулевой вес не выбирается; отрицательные/нечисловые веса и полностью нулевая подходящая группа диагностируются.

Идентификатор `CenterSuperTreasureZoneWithCity ` содержит конечный пробел. В текущем файле ссылки используют тот же точный идентификатор; это не основание «исправить» имя через Trim. `NativeSchemaDocument` сравнивает названия ordinal, сохраняет массивы, дробные числа, комментарии в виде `_...` свойств и неизвестные поля. JSON formatting и комментарии вне JSON могут измениться при сериализации.

`MapgenSourceMode.Schema` найден в namespace `Hex.MapGenerator.Tests`; это debug source mode. `ScCustomTemplate` содержит настройку размера, героев, игроков, богатства, сложности, симметрии и победы. В его входной модели `czl` отдельный выбираемый пользовательский schema identifier не найден. Существование debug mode не доказывает поддержанный пользовательский путь запуска произвольного `.mrmg`.

`bmo.nde` RVA `0x2A6E960` преобразует строку схемы в объект и передаёт его в `bpp.npc`. Вызов зависим от Unity/IL2CPP; он не является самостоятельным API библиотеки для WPF. Полный путь чтения конкретного файла, регистрации в меню и сохранения native результата в `.rmg.json` не установлен. Aurora сохраняет изменённую схему как отдельный исследовательский файл, не подменяя `Default.mrmg.json` в игре и не устанавливая её в `map_templates`.

### Подтверждённая единица per-area бюджета (C-04)

`blq.mya` RVA `0x2A2DC90` получает счётчик площади через `blq.myb` RVA `0x2A2E380`. Бюджеты guarded, unguarded и resources вычисляются независимо по формуле `absolute + RoundToEven(effectiveFreeCells × perAreaCoefficient × 0.1f)`. Из машинного кода и RIP literal в RVA `0x2A2DFAD` подтверждён множитель `0.10000000149011612` (float). Короткий helper `blq.myc` RVA `0x2A2E770` содержит ту же формулу. Native rounding helper в RVA `0x14B53E0` при половине проверяет чётность целой части.

`effectiveFreeCells` не равен числу всех клеток зоны: counter создаёт маску `ObstacleState.AlwaysFree = 5`, расширяет её пятью проходами по соседям, затем считает только клетки с установленной маской, `ObstacleState.Free = 0` и совпадающим zone ID. Проверка Free подтверждена в extension `nud` RVA `0x2B37BB0`: `test cl, cl; sete al`.

Следовательно, коэффициент можно описывать как бюджет на десять подходящих свободных клеток около зарезервированных путей. Подставлять `mapSize² × zoneWeight` вместо этого счётчика нельзя. `NativeAreaBudget.Calculate` реализует точную арифметику при известном effective count, с отказом на overflow/negative inputs. При экспорте native профиля движок сам определяет счётчик; Aurora может записать наблюдённый perArea coefficient с absolute=0. Перевод legacy абсолютных бюджетов через предполагаемую геометрическую площадь не считается сохранением прежней экономики.

В каждой из 14 зон установленной схемы `randomHireEnableWeeklyUnitIncrement` имеет семь значений true, `randomHireInitialUnitIncrement` — семь значений 1. Это подтверждает формат текущего native профиля для роста найма. Массивы импортированных legacy шаблонов другой длины сохраняются без автоматического обрезания.

### Подтверждённый порядок реакции охраны (C-03)

Native `ESquadReactionType`: Aggressive=0, Negative=1, Common=2, Friendly=3, Peaceful=4, Docile=5. Проверка фактического использования массива проведена отдельно от чтения enum: `bmd.nav` RVA `0x2A554C0` вызывает weighted index selector в RVA `0x2A55524`, после чего передаёт returned index напрямую в аргумент `ESquadReactionType` (RVA `0x2A55549`). `SquadParams.ncb` RVA `0x2A576D0` записывает этот аргумент без перестановки в `disposition` (RVA `0x2A57707`).

Следовательно, первый вес относится к наиболее агрессивной реакции, последний — к Docile. Историческое описание Aurora обратного порядка ошибочно. Новые профили агрессии должны учитывать нативный порядок; сохранение historical raw output legacy профиля — отдельное требование воспроизводимости, а не подтверждение правильности старых подписей.

## R-02: конфигурация native генерации

`RmgSchemaSettings.mtj` RVA `0x29DEE90` и `mtk` RVA `0x29DF1B0` позволяют определить компактный формат. Биты идут от младшего к старшему внутри байта; итог — обычный Base64. Поля:

| Поле | Биты | Особенность |
|---|---:|---|
| flags | 16 | Native ushort flags |
| size / 16 | 5 | Размер делится на 16 при записи, умножается при чтении |
| spawnCount | 3 | Записывается прямо, без `−1` |
| richness | 4 | Текущий профиль имеет 0–4 |
| difficulty | 4 | Условия текущей схемы имеют 0–5 |
| finalBattleDay | 8 | Только при `FinalBattleWinCon` |
| tournamentDays.Count | 3 | Только при `TournamentWinCon`; decoder требует ненулевой count |
| каждый tournamentDays[i] | 8 | Последовательно после count |

Нативный writer имеет буфер 16 байт; последний неполный байт дополнен нулями. `heroCountMin`, `heroCountMax`, seed, factions и spawnInfos в этом коде отсутствуют. Aurora не подставляет отсутствующие лимиты героев и не выдаёт такой импорт за восстановление старого матча. При кодировании JSON с непредставимыми полями происходит отказ с предложением сохранить JSON. Восемь игроков сохраняются в JSON; данный компактный writer не может представить число 8 в трёх битах. Не следует незаметно кодировать их как 0 или вычитать один.

Изолированный `NativeConfigurationCodec`:

- Принимает JSON native settings с `flags` и debug input с boolean flags, сохраняя остальные поля.
- Отличает inputs от `.mrmg`, `.rmg`, карты и save по наличию `size`/`spawnCount`.
- Читает подтверждённый компактный формат, отклоняет усечённый payload, неизвестные flags и лишние байты/ненулевой padding.
- Отдаёт raw календарные поля без предполагаемого преобразования в готовые `.rmg` дни. Перевод в правила карты выполняется отдельно основным генератором.

`NativeConfigurationImporter` создаёт независимую копию настроек Aurora: точные размер, число игроков, заданные лимиты героев, индексы богатства/опасности и поддержанные условия победы. Отсутствующие поля не подменяются: компактный код сохраняет текущие лимиты героев. Нативные календарные дни переводятся в пользовательские через `+1`. Unknown inputs, seed игры и неустановленные random-team правила остаются в raw payload с отдельной диагностикой; seed игры не выдаётся за seed шаблона Aurora. Нативное HoldCapital соответствует работающему Aurora `win_condition_3` с `lostStartCity`, а не неподтверждённому захвату столицы `_2`.

При передаче схемы импортируются точные `river.createRiverSystem/tributarySpacing` и только константные настройки роста, совпадающие во всех соответствующих main object classes и семи слотах random hire. Условные или отличающиеся по ролям значения не сплющиваются в общий переключатель. Настройки магии отсутствуют в native input contract и не угадываются по одноимённым unknown полям. Quick mode сохраняет собственную размерную категорию и предупреждает, что точные размер, hero mode и комбинации победы нужно использовать через Advanced.

`NativeSchemaEditorWindow` предоставляет офлайн дерево точных идентификаторов, структурированные AND/OR, weight/fallback/value и raw JSON с unknown полями. Правка применяется транзакционно; переход к другому узлу/разделу с неприменённым текстом заблокирован без его потери. Save As по умолчанию создаёт отдельную копию и запрещает запись в известную папку игры. Это возможность редактирования, а не доказательство выбора custom `.mrmg` в игровом picker.

После проверки UI conversion установлено: native settings используют zero-based дни. `czl.wzc` RVA `0x2F29E40` вычисляет `Day + 7×Week + 28×Month − 36`; для Д1/Н1/М1 получается 0, для второго игрового дня — 1. Поэтому импорт даты в пользовательский календарь добавляет 1. `bpp.npf` добавляет 1 к raw `finalBattleDay`, записывая delay в `.rmg`: это фактически выбранный пользователем абсолютный игровой день, а не пользовательский день плюс один. Native raw tournament day 0 запрещён; raw day 1 — допустимый второй игровой день. Компактный календарь хранит максимум raw 255, соответствующий игровому дню 256.

В нативных данных есть `MapData`, `GeneratedMap`, `WinConditionsData` и session save types. Из этих классов не следует, что в save сохранены исходные zone classes, content budgets и template connections в форме, пригодной для восстановления шаблона. Импортер save/map не создаётся на основе такого предположения.

## R-03: столица и важные объекты

### Лимит героев и начальное создание

В интерфейсе Aurora поле называется «Начальный лимит героев». Его контракт относится к вместимости найма: неотрицательная база и прирост за принадлежащие игроку города. Проверка текущего профиля отклоняет запрос точной вместимости ниже уже заданного прироста от стартовых городов. Это не утверждение о количестве создаваемых стартовых героев. Отдельный путь initial hero creation не доказан разобранным writer; количество героев и найм при нескольких стартовых городах входят в ручную приёмку.

`RmgSchemaSettingsFlags.HoldCapitalWinCon = 8` действительно существует. В `bpp.npf` RVA `0x2AF3FB0` этот флаг записывает `winConditions.lostStartCity = true` и `lostStartCityDay = 3`. `HoldCityWinCon = 16` записывает `cityHold = true` и `cityHoldDays = 3`; `StartingHeroWinCon = 32` записывает `lostStartHero = true`. Эти преобразования — факты, но не доказательство всех союзных сценариев победы.

В реальном `WinConditions` нет отдельного RMG поля «Битва за столицу». В `TypeWinCondition` есть `InteractWO`, `LostImportantHero`, `CityHold`, `LostStartCity`, `GladiatorArena` и другие map/campaign правила. Числа enum не совпадают с суффиксами локализации `win_condition_N`, и создавать произвольный «номер победы» на этой основе нельзя.

`MainObject.isKeyObject` и `holdCityWinCon` подтверждены. Основная реализация может использовать их для поддержанных целей. Для `_2`/`_7` нужны самостоятельные подтверждения перехода объекта/боя, привязки цели, проигравшей стороны и итогового сообщения. Пока этого нет, отдельные обещающие эти режимы варианты в основном UI не раскрываются. Исходные неизвестные поля импортированных шаблонов сохраняются.

## R-04: турнир и финальная битва на многих игроков

Ограничение связано с несколькими слоями, и их нельзя смешивать.

1. `ScCustomTemplate.czm` содержит собственные сообщения `random_map_tournament_two_players_only` и `random_map_final_battle_two_players_only`. Это подтверждает проверку Quick Start UI.
2. `bpp.npf` в RVA `0x2AF4063` проверяет native `spawnCount == 2` для Final Battle. Несовместимы simultaneous Tournament/FinalBattle и эти правила с Classic/HoldCapital/HoldCity.
3. Session backend турнира `fpo.bmwl`, RVA `0x24D2F10`, при инициализации выделяет `WinConditionData.pointsTournament` как массив из двух элементов: `mov edx, 2` в RVA `0x24D3006`, затем array allocation и запись в offset `0x60`. В RVA `0x24D3083` задаётся `bjsx(2)`, инициализация пары `dataForFight.idHeroes`.

Таким образом, есть реальное backend свидетельство пары и двух счётов. Этого достаточно, чтобы не обещать собственный круговой турнир на 3–8 участников с одним списком дней. Это не утверждение, что ни один будущий/альтернативный session handler или отдельная карта игры не сможет поддержать иной формат. Альтернативный поддержанный `.rmg` contract для большого турнира не найден; две большие команды не приравниваются автоматически к двум scoring sides.

Поле `winnerSides` — массив, `tournamentDays` — список дней. Эти общие контейнеры сами по себе не доказывают подбор пар, bracket и next round. Для полноценного многопользовательского турнира потребуется соответствующая поддержка игры либо отдельный проверенный сценарный механизм.

## R-05: порталы и fallback

Native `ConnectionType` содержит `Default`, `Direct`, `GladiatorArena`, `Portal`, `Proximity`. Реальный `RmgTemplate.Connection` имеет отдельные boolean `portalFromEnabled`/`portalToEnabled`, placement lists для обеих сторон, группы и реакцию охраны. Конструктор устанавливает направления в true.

Fallback установлен в `bnl.gua` RVA `0x2AA2890`, преобразующем layout в конечные соединения. В RVA `0x2AA2A13` читается тип соединения. Для `Direct = 1` при false в gate result тип заменяется на `Portal = 3` (RVA `0x2AA2A39`). Для `Default = 0` выбирается Portal, а при true в gate result — Direct (RVA `0x2AA2A4B`–`0x2AA2A55`). `Proximity = 4` обрабатывается отдельно. Это подтверждение реального перехода Direct→Portal, а не вывод из наблюдения локализованного описания.

Наличие направлений подтверждает возможность задавать travel/placement поля портала. Связь `portalFromEnabled`/`portalToEnabled` с предшествующим выбором gate result не установлена; полного поддержанного параметра «запретить fallback» не найдено. Все этапы создания/резервирования прохода не восстановлены.

Поэтому «Добавлять дополнительные порталы» описывает только собственный генератор Aurora. Выключение этой функции не формирует недоказанную гарантию отсутствия любых порталов в игровом результате. Строгая политика требует отдельного подтверждённого набора полей и проверки множества seeds именно в игре; простой экспорт `Direct` и `portalFromEnabled=false/portalToEnabled=false` этой проверки не заменяет.

Для refactor проверен `PlacementRuleType`: Random, Sid, MainObject, Crossroads, Connection, Road, MandatoryContent. `NearZone` — другой enum для gate/main object placement, а не подтверждённый тип portal placement rule. В resolver `nke` RVA `0x2AB17A0` ветка Connection=4 передаёт args[0] в `ntp` RVA `0x2B34C50`; он ищет connection по имени и проверяет связь с текущей зоной. MainObject=2 использует локальный индекс объекта текущего endpoint. Поэтому rename/delete/mirror безопасно обновляют подтверждённые имена и локальные индексы; неизвестные типы сохраняются с явным предупреждением, а не переписываются поиском совпадающего текста.

GladiatorArena=2 участвует в физической gate/zone geometry: `nui` RVA `0x2B37C30` возвращает true для Direct=1 и Arena=2, `nuj` RVA `0x2B37C40` — для Default=0, Direct=1, Arena=2. Вызовы этих predicates найдены в rasterizer `bon.bpm/cus` и gate target resolvers `boy.ctr/noy`; `bnl.gua` сохраняет type2 и передаёт обычный gate result. Это не игнорируемое виртуальное турнирное ребро. Однако возможность героя пройти после конкретного взаимодействия на арене не установлена; потенциал короткого прохода учитывается консервативно, игровая проверка выделена отдельно.

## R-06: AI и новые крупные режимы

Из `Core.zip/DB/ai_world/ai/*.json` извлечены реальные верхние `array[].id`, а не названия файлов. Например, файл `multi_hero_1_easy.json` содержит ID `multi_hero_easy`. Native `AiConfig` использует string key; `MapDataSettings.enableCustomAI/customAISid` и `GameRules.customAI` реально существуют.

Текущий некампанийный набор:

- `multi_hero_easy`, `multi_hero_normal`, `multi_hero_complicated`, `multi_hero_hard`, `multi_hero_unfair`.
- `one_hero_easy`, `one_hero_normal`, `one_hero_complicated`, `one_hero_hard`, `one_hero_unfair`.
- `custom_ai_multi_hero`, `custom_ai_one_hero`, `custom_ai_none_multi_hero`, `custom_ai_none_one_hero`, `custom_ai_test`.

`custom_ai_none_*` содержит роли, хотя списки actions пусты. Название `none` нельзя переводить как «ИИ ничего не делает» без анализа задач ролей и фактического матча. `custom_ai_test` — проверочный профиль, а кампанийные ID связаны с конкретными сценариями. Каталог возвращает ID, источник, roles и action SIDs; интерфейс должен явно отличать обычные, custom/test и кампанийные варианты и не обещать «менее агрессивный ИИ» по названию.

Мореходство, подземелье, произвольная загрузка native DLL, новые режимы из будущих beta и неизвестные типы сущностей не реализуются через выдуманные поля. Текущий формат сохраняется и поддерживает будущие unknown значения, но их эффект не заявляется до отдельного подтверждения.

## Исходники и проверка

Собственная реализация находится в `Models/NativeSchema/` и `Services/NativeSchema/`; synthetic tests — `NativeSchemaTests.cs`, `NativeConfigurationImportTests.cs`, `PortalPlacementRefactorTests.cs`. В исходники не включены игровой `Default.mrmg.json`, DB целиком, disassembly или dump.cs. Фактические локальные данные загружаются при чтении установленной игры.

Офлайн `PatchAcceptanceSuite` последовательно проверяет исходный установленный корпус и все 53 patch presets на двух фиксированных seeds, а также отдельные сценарии новых полей. Raw→typed→JSON сравнение проходит все варианты и unknown поля; разрешённые collapsed collection/null нормализации фиксируются отдельно. Новые шаблоны проходят строгую проверку по установленному полному каталогу, проверку запрошенных полей, повторяемости и повторного JSON импорта. Результаты и 20 пар `.rmg.json`/`.oetgs` для ручной проверки создаются только вне игры; failed cases завершают suite ошибкой после сохранения отчёта. `manual-results.json` изначально имеет статус pending, а успешная офлайн проверка не заменяет игровую приёмку.

Ключевые регрессии: точный SID с конечным пробелом, unknown round-trip, массивы и дробные значения, weighted fallback, AND/OR и границы, отказ при неизвестном условии, независимые Base64 fixtures, отсутствие выдуманных hero limits, невозможность бесшумно обрезать 8 игроков, получение AI ID из массива базы. Запуск build/tests централизован и выполняется с низким приоритетом; результаты фиксируются в общем отчёте выполнения плана.

## Воспроизводимый офлайн прогон

Команды запускаются последовательно из корня репозитория. Helper сериализует проверки общим mutex, использует Idle priority, один разрешённый logical CPU и отдельную временную папку preferences/cache. Новый UI harness рендерит свои окна вне экрана без активации игры. Нельзя считать PNG проверкой игровых побед, размещения объектов или пользовательского ручного матча.

```powershell
pwsh -NoProfile -File .\scripts\Invoke-LowImpactChecks.ps1 -Mode BuildAndTest

$patchCheckRoot = Join-Path ([IO.Path]::GetTempPath()) ('AuroraRMG-patch-acceptance-' + [DateTime]::Now.ToString('yyyyMMdd-HHmmss'))
pwsh -NoProfile -File .\scripts\Invoke-PatchAcceptance.ps1 -Mode Ui -Language ru -OutputDirectory (Join-Path $patchCheckRoot 'ui-ru') -GameInstallPath 'G:\Steam\steamapps\common\Heroes of Might and Magic Olden Era'
pwsh -NoProfile -File .\scripts\Invoke-PatchAcceptance.ps1 -Mode Ui -Language en -OutputDirectory (Join-Path $patchCheckRoot 'ui-en') -GameInstallPath 'G:\Steam\steamapps\common\Heroes of Might and Magic Olden Era'
pwsh -NoProfile -File .\scripts\Invoke-PatchAcceptance.ps1 -Mode Kit -Language ru -OutputDirectory (Join-Path $patchCheckRoot 'kit') -GameInstallPath 'G:\Steam\steamapps\common\Heroes of Might and Magic Olden Era'
```

Папки результата должны быть новыми или пустыми. `acceptance-report.json` отделяет неизменность исходного корпуса и tolerant diagnostics от строгой проверки новых шаблонов. `manifest.json` содержит SHA-256 созданных файлов и fingerprints источника, `manual-kit` — 20 отдельных сценариев с полными `.oetgs` снимками и `.rmg.json`. `manual-results.json` имеет pending до фактического заполнения владельцем; инструкция RU/EN требует проверять lobby/hotseat, игровые seeds, вторую неделю, победы, сохранение и загрузку. При failed case, отмене или исключении процесс возвращает ошибку и сохраняет доступный диагностический результат.
